# Security

kiln runs other people's code, or at least your own code at its least trusted, on a machine you care about. This document describes what kiln assumes, what it defends, what it does not, and how to report a problem.

## Threat model

**A job is root in its VM.** The runner user has passwordless `sudo`, and the workflow can run anything. kiln assumes a job is hostile (a malicious pull request, a compromised dependency) and that it can print anything on the VM's console, use the network the VM is given, and try to outlive its timeout.

What kiln protects:

- the host and its other files and processes;
- your LAN and tailnet, and other machines on them;
- the forge tokens (GitHub, GitLab, Gitea) and the dashboard;
- other jobs, and the integrity of the repo cache and the base image;
- the Docker mirror's contents.

Out of scope: a QEMU or KVM escape or a Linux kernel bug (keep the host patched), a malicious owner of the box, and anyone who already has an account on the host (the dashboard key and token files are readable by that user).

## What kiln defends

### Dashboard and API access

The dashboard holds forge tokens and can kill VMs, so access is checked on every request:

- **Tailnet identity.** A request from a tailnet address is mapped to a user with `tailscale whois`. By default only the owner of the CI box is allowed, which keeps out nodes shared in from other tailnets. `allowed_users` replaces that list. Tagged nodes (`tagged-devices`) are never allowed by default and only get in if listed explicitly.
- **HTTPS through `tailscale serve`.** Serve over HTTPS proxies to the unix socket `<data>/serve.sock` (mode 0600, owned by the kiln user), not to the TCP port. tailscaled (root) can connect to it; job VMs cannot reach a unix socket, and other local users lack the permission. kiln reads the connecting process's uid (`SO_PEERCRED`) and trusts identity headers only from root: a process running as the kiln user, including a job VM's confined QEMU on a kernel without Landlock socket scoping, gets the same treatment as a local request and needs the dashboard key. Only on that socket does kiln read the `Tailscale-User-Login` and `X-Forwarded-For` headers, which tailscaled overwrites with the tailnet user and source address it saw. The login must match what `tailscale whois` says about that address, and is checked against the same `allowed_users` rule. A serve request without a login (a tagged node) is identified with `tailscale whois` exactly as over TCP, so a tagged node is refused unless `tagged-devices` is listed. A request from the box's own tailnet address or node (tailscaled names the box's owner for those, and a job VM can reach the box's address through QEMU's NAT) is treated as local and needs the dashboard key; an address kiln does not recognize makes it re-read its own addresses (at most every 10 s) first. A Funnel request (`Tailscale-Funnel-Request`, the public internet) is refused. On the TCP port these headers are ignored: anyone can send them there.
- **Never TCP-forward or funnel `serve.sock`.** tailscaled overwrites the identity headers only in its HTTPS reverse proxy (`tailscale serve --https=… unix:…`). A raw TCP forward to the socket (`--tcp`, `--tls-terminated-tcp`) passes the client's bytes through, headers included, and Funnel opens the port to the internet. kiln reads `tailscale serve status --json` (cached for a minute, re-read when Serve is toggled from the dashboard) and trusts the socket's headers only while every handler that targets it is a Web proxy on a port without Funnel. Otherwise, or when tailscale can't be asked, every request on the socket is treated as local and needs the dashboard key; kiln logs a warning and `kiln doctor` fails the "tailscale serve" check.
- **Dashboard key for local requests.** Requests from the box itself (loopback, the box's own tailnet IP) need the key in `<data>/dashboard.key` (mode 0600, 24 random bytes from `/dev/urandom`, compared in constant time). The source address cannot be trusted for these because job VMs reach the host through QEMU's NAT and look exactly like local traffic. If kiln cannot read its own Tailscale identity (for example while Tailscale is down), only loopback and tailnet addresses are admitted, and both need the dashboard key.
- **Everything else is refused:** the LAN, the public internet, and anything not on the tailnet.
- **Host header check.** The `Host` (through `tailscale serve`, the `X-Forwarded-Host` tailscaled sets) must be an IP, `localhost`, a `*.ts.net` name or a single-label MagicDNS name. This blocks DNS rebinding.
- **CSRF header.** Every non-GET request to `/api/` needs the custom `x-kiln` header, which a browser cannot add cross-origin without a CORS preflight that kiln never grants.
- **Typed forge endpoints.** The dashboard reads runs, jobs, logs and workflows through `/api/forges`, `/api/runs`, `/api/runs/{id}`, `/api/jobs/{id}/log` and `/api/workflows`, which return kiln's own JSON. Every call names its repo as `repo=<canonical key>`, which must be one kiln serves; no forge path comes from the browser, run and job ids are numeric, and a dispatch workflow is a plain file name or id. The only writes are rerun, cancel and dispatch (`POST /api/runs/{id}/rerun`, `/api/runs/{id}/cancel`, `/api/dispatch`), each needing the forge to allow it (on GitLab, a token with the `api` scope), the `x-kiln` header (CSRF) and an audit-log line, and forge management (`POST /api/forges`, `/api/forges/{id}/token`, `/check`, `/repos`, `DELETE /api/forges/{id}`), which has the same header and audit line, raises a security alert for add, remove, token and project-list changes, never returns a token, and cannot move an existing forge to another address through the dashboard: a config save that changes a forge's address, kind, token source or network is refused, and forges are added and removed only through these endpoints (an add always uses a saved token file, never an environment variable), so a token never follows a forge id to a new address. Editing `config.json` by hand is the owner's own action and is not guarded. Runners, secrets, variables, run approvals and deployment reviews are unreachable. The forge's log download is capped, not just the part kiln returns.
- **Response headers.** A strict `Content-Security-Policy`: `default-src 'none'`, scripts only by the SHA-256 of the page's own inline blocks (computed from the embedded page at startup), connections to the same origin only, forms only to `https://github.com`, no framing, no `<base>`. An injected script or handler does not run even if some string slipped past the page's HTML escaping, which matters because the page holds the dashboard key. Also `X-Content-Type-Options: nosniff`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`, a `Permissions-Policy` denying camera, microphone, location, USB and payment, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and `Cache-Control: no-store` on API responses. The page only links to URLs under a forge's own web address (from `/api/forges`) that it gets from the API.
- **Audit log.** Every admitted API write is appended to `<data>/audit.log` (mode 0600, rolled over at 8 MiB, also written to kiln's log); refused writes are logged to kiln's log only, so a job cannot flood the file: when, the tailnet login or `local`, the source address, method, path, status, and what changed (the keys of a config save, the repo of a cache clear). Ship it to your log pipeline if you need it kept.
- **Bounded identity lookups.** The `tailscale` CLI calls the guard depends on are killed after 20 seconds; a timeout counts as an unknown identity, which is refused, or, when kiln cannot learn its own addresses at all, as local, which needs the dashboard key.
- Forge tokens (the GitHub token, and `<data>/forges/<id>.token`) are stored with mode 0600 and never included in error messages. A job VM only ever receives a runner credential limited to one job, in one of three shapes: on GitHub a single-use JIT runner configuration, enforced by GitHub; on GitLab a `glrt-` runner token for one project that kiln pauses before the verdict, never unpauses and deletes when the VM ends (see [GitLab](#gitlab)); on Gitea a single-job runner credential that kiln deletes when the job ends. The host's copy is deleted as soon as the guest has read it.
- **A Gitea account is more powerful than a GitHub App** (Gitea): the account behind kiln's token must be the repo's Owner. See [Token power](#gitea) under Gitea. A Gitea older than 1.25 is refused.

### VM isolation

Each job runs in its own QEMU/KVM guest (Hypervisor.framework on macOS) on a throwaway qcow2 overlay, so nothing survives the job. QEMU runs as your unprivileged user, with no tap devices, bridges or sudo. The job's disk, JIT secret and sockets are deleted when the VM ends, and runners that never ran are deregistered.

### VMM confinement

A QEMU escape is out of scope, but kiln limits what one would gain, as libvirt does for its guests:

- **seccomp (Linux):** every QEMU kiln starts on Linux runs with `-sandbox on,obsolete=deny,elevateprivileges=deny,spawn=deny,resourcecontrol=deny`, so an escaped QEMU cannot start a shell or any other program, gain privileges or use obsolete syscalls. A QEMU without seccomp support refuses the option and no VM starts.
- **No seccomp and no Landlock on macOS.** QEMU on Apple Silicon is started without `-sandbox` and without `kiln __confine`, so a QEMU escape there runs with the kiln user's full rights and reaches every file that user can read, forge tokens and the dashboard key included. Do not run untrusted code on a Mac kiln.
- **Landlock (Linux):** a job VM's QEMU is started through `kiln __confine`, which restricts it to the system directories (read-only), `/dev/kvm` and the standard character devices, the images directory and its own repo's cache disk (read-only), and its VM's `q/` directory (disks, JIT secret, sockets). It cannot read any forge token, `<data>/forges/` included (it inherits only a short allow list of kiln's environment variables, `PATH`, `HOME`, `USER`, `LANG` and a few more, never a token or credential), the App key, the dashboard key, other jobs' files or other repos' caches, cannot open its own VM record or logs (only append to the console log through its stdout and stderr), and cannot ptrace kiln or other VMs; on Linux 6.12+ it also cannot signal them or use abstract unix sockets; with the newest Landlock ABI it cannot connect to unix sockets such as tailscaled's or Docker's. Landlock is best effort: `kiln doctor` and kiln's startup log report what the kernel enforces, and a VM started without it says so on its job page. kiln refuses to start with its data directory under a path QEMU may read (`/usr`, `/lib`, `/lib64`, `/bin`, `/etc`, `/opt`, `/proc`, `/sys`). kiln connects to QEMU's monitor and step sockets without following links, so a planted symlink cannot point it at another VM's socket. A trusted cache overlay is committed only after `qemu-img info` shows a plain qcow2 file backed by exactly that repo's cache disk, with no external data file, so a compromised QEMU cannot steer the commit into another file.

### Files on the host

The data directory is set to mode 0700 at every start, and the systemd unit sets `UMask=0077`: job logs (which may contain what a job printed), repo caches, VM disks and the key files are private to the kiln user. Secret files (token, App key, dashboard key) are written atomically with mode 0600 even when a looser file existed. `config.json` is validated at startup and kiln refuses to start on an invalid one, so a hand-edited typo cannot weaken a setting (for example an `egress` value that is neither `open` nor `filtered`).

### Filtered egress

With `egress: "filtered"` each job's QEMU runs in its own rootless network namespace with an nftables allow-list loaded first, and then drops all capabilities. Jobs reach the public internet, DNS and the Docker mirror port only (plus, for a GitLab or Gitea forge with `network: internal`, that forge's `ip:port` and nothing else private; the forge `url` must then be an IPv4 literal, never resolved from a DNS name, so whoever controls a name cannot aim the hole at another host; a loopback, host-own, link-local, slirp (10.0.2.0/24, which includes the host's loopback alias) or port-25 forge is refused; and because the rule is by address, every site behind a shared reverse proxy on that address becomes reachable too); the LAN, tailnet, the host's own addresses, cloud metadata addresses, every other host loopback port and outbound SMTP are blocked, and IPv6 is off. If any setup step fails, QEMU never starts. A probe verifies the filter and kiln launches nothing while it fails, never falling back to open. See [docs/architecture.md](docs/architecture.md#egress).

### Cache trust

The per-repo cache disk follows a trusted-writer, throwaway-reader rule. Every job gets a private overlay, and an overlay is merged back only when the job succeeded according to the forge's API (not just the console), the event was a `push`, the branch is the default branch or one of the repo's `cache_branches`, and the commit is really on that branch. A branch name outside `A-Z a-z 0-9 . _ / -` (or containing `..`) never writes. A pull request can read the cache but never poison it. The decision uses the forge's data because the job controls its own console output.

Release builds do not read the cache at all: a job for a pushed tag or a `release` event detaches it before its first step and runs on the clean base image, so a dependency compromised in some default-branch job cannot plant a toolchain that ends up in what you ship. After every job, login tokens that tools write under cached paths (`cargo login`, `huggingface-cli login`) are deleted before the cache can be saved. See [docs/architecture.md](docs/architecture.md#release-builds-run-cold).

### Actions cache

With `gha_cache` on, kiln serves `actions/cache` from `127.0.0.1:5001`. The guest is untrusted, so identity comes from the kernel: the peer socket's inode in `/proc/net/tcp`, the process that owns it, and that process's `kiln-vm-<id>.scope` cgroup (or the pid kiln started for the VM where there is no systemd). The request, including its token, never picks the VM or the repo; a token naming a different runner than the VM's makes the request unidentified, and an unidentified peer is proxied to GitHub untouched. A job's writes are staged per VM and promoted into the repo's trusted scope only on the verdict that commits the cache disk, so a pull request or a failed job can read the cache but not poison it; every other way a VM ends deletes its staged entries. Repos are keyed by the hash of their forge kind, host and full path (so `acme/my.repo` and `acme/my_repo` never share a directory), and each entry stores that identity, which is checked on every read, download and promotion.

### Fork pull requests

kiln refuses to run code from a fork. The scheduler does not count queued jobs of runs whose head repository differs from the repository (or is gone), so on GitHub they never boot a VM of their own (on Gitea a queued fork job can still cost one VM, see [Gitea](#gitea)), and the dashboard lists them as refused. Because a JIT runner can still be handed any queued job with matching labels, every VM also runs a runner job-started hook before the job's first step: if the event is a pull request (`pull_request` or `pull_request_target`) from another repository, or a `workflow_run` whose triggering run's head repository is another one, it fails the job right there, and kiln kills the VM when it sees the assignment. It fails closed: a deleted fork, a `workflow_run` with no head repository, or an unreadable event payload are refused too. This is enforced whatever the workflow says; the `if:` guard in the workflows is a second layer.

The hook can only see where the event came from, not what the workflow then checks out. Workflows triggered by `issue_comment`, `repository_dispatch` or `workflow_dispatch` (or anything else) that check out a pull request's head, such as a "/test" comment bot, run fork code that kiln cannot detect. On a public repository such workflows must not run on kiln: give them a GitHub-hosted runner.

On Gitea the cache disk is the only cache that persists: the runner's own `actions/cache` server and work directory are on the VM's disk and are thrown away with it, so a job cannot plant anything there for a later one. On every forge, dockerd is not started at boot, and when the disk is mounted everything in the cached `/var/lib/docker` except `image`, `overlay2`, `volumes` and `buildkit` is deleted (container records, plugins, swarm state, networks), so a container or swarm service planted in the cache by a compromised trusted job (a restart policy, `docker service create`) has nothing to restore. GitLab starts dockerd only after the job's trust step (`kiln-exec`, the verdict) and Gitea only after `kiln-docker-gate` sees the verdict, and on a cold run only after the cache disk is detached. GitHub does not start it at all: `docker.socket` activates it on the first use, and the runner's job-started hook (which makes the tag and release cold-detach decision) runs in "Set up job", before the first container step; a release job's detach stops the socket and dockerd and starts a fresh one on the clean disk.

GitLab merge request, downstream and tag handling is under [GitLab](#gitlab) below.

### Gitea

Gitea (1.25 or newer; end-to-end tested on 28.1.0 with `gitea-runner` 5.0.0) is a first-class forge. Its runner cannot be told which job to take, and a Gitea runner starts running a job the moment it fetches it, so the guard is inside the VM: a root **exec gate** holds every process the runner starts until the host's verdict arrives. The whole path was tested end to end (plain, `container:` and `services:` jobs, tags, fork pull requests, `pull_request_target`, `workflow_run`, cache poisoning attempt, gate death as the host sees it, filtered egress).

**Guarantees**

- **No job code before the verdict.** `kiln-gate` marks every filesystem with fanotify `FAN_OPEN_EXEC_PERM` and holds each exec by the runner, any process of the `runner` user or any process it cannot see, until the host says `ok` or `cold`. A `uses: http://...` action, a `run:` step, a `container:` or `services:` start and the Docker socket are all behind it: in the end-to-end test a first step calling a listener produced zero connections for a refused fork job. `vm.memfd_noexec=2` closes the memfd route. The only process that runs before the verdict is the Gitea runner binary itself (pinned by version and SHA-256); re-test the gate battery whenever it is bumped.
- **Two gates.** Two independent gate processes watch; if either dies before a verdict, the runner's processes are killed, the guest prints `kiln.gate=dead` and powers off, and kiln kills the VM and discards the cache overlay. A VM that ends between job start and verdict counts as a dead gate even if the line never arrives.
- **Docker is gated too.** dockerd is not started at boot; it starts only after the verdict (and, on a cold run, after the cache disk is detached). The cache's container records are deleted when the disk is mounted, so a restart-always container planted by a compromised trusted job never runs (tested).
- **The verdict binds this runner's job.** The host reads the job id from the runner's `task started` console line, then requires from the Gitea API that the job is in progress on this VM's own runner and belongs to the served repo; any lookup error refuses.
- **Forks and non-push sources are refused.** Pull requests whose head repo differs (including a repeat contributor, whose run needs no approval, and a run a maintainer approved), `pull_request_target` from a fork, and every `workflow_run` are refused with no job code run, the VM is killed and the cache discarded. The dashboard shows a banner while such a job is queued, but launches go on: a VM that is handed the job is refused by the gate and killed, so each queued fork job can cost one VM (see the residual risks). A job with more than one label other than the size label is invisible to kiln's queue accounting; the gate still refuses it. Tags and releases run cold.
- **Cache writes only for trusted pushes,** judged by the host from the API (the job succeeded on this VM's runner with a recorded `ok` verdict). As on GitHub, a `cache_branches` entry need not be a protected branch on Gitea (GitLab requires protection), so list only branches as protected as the default. Gitea's own `actions/cache` does not persist: its server and work directory are on the VM disk.
- **The runner credential is single-job.** The VM gets an ephemeral runner credential for one job in one repo; kiln deletes the runner when the VM ends (a runner whose job Gitea still shows running is disabled at once and deleted once the job leaves that state, or at the next start or hourly sweep).

**Token power.** kiln's Gitea token (`write:repository`, `read:user`) belongs to an account that must be the repo's **Owner** (Gitea gives the runner registration token only to an Owner). That account can push, change the repo's settings and, in the worst case, delete it; the registration token it obtains is reusable and registers more runners. Use a dedicated account that owns only the repos kiln serves, and the token for nothing else. kiln keeps the registration token in memory only, and the setup UI says all of this next to the token field. Before 1.26.3, approving one fork pull request once trusts that user's later ones (the dashboard warns); the gate refuses their jobs regardless.

**Residual risks**

- **Both gates dying at the same instant** frees the pending exec (the kernel releases the group). It needs root in the guest or a kernel failure and is not reachable by the job before the verdict; `oom_score_adj` -1000, an unlimited queue and a loop-level deny-and-kill handler narrow it. Single-gate death was tested in a VM and fails closed: the dying gate first resets the VM with sysrq `b`, so the held execs die with the VM instead of being released.
- **A refused job stays `in_progress` in Gitea** (its runner is gone) until it is cancelled or Gitea's zombie-task timeout ends it.
- **Your own branches and approved collaborators** run with the cache like any trusted code; anything the job writes under the cache disk is visible to later trusted jobs.
- **Each queued fork job can burn one VM.** A runner takes the oldest job it matches, so a fork, `pull_request_target` or `workflow_run` job that reaches a VM is refused and the VM is killed (about 10 s later) before a legitimate job runs. A contributor can stage many such jobs (with two kiln labels, kiln does not even count them); the cost is bounded at one VM per staged job. Require approval for all fork pull requests on the forge.
- **Gitea below 1.25, Forgejo and arm64** are not supported or not tested.

### GitLab

GitLab (gitlab.com or self-managed, 16.0 or newer) is a first-class forge. A GitLab runner is not bound to one job in advance the way a GitHub JIT runner is, so kiln adds a host-side gate and keeps the runner credential single-job by other means. The whole path was tested end to end against GitLab CE 19.4.1; what was not tested is listed under residual risks below.

**Guarantees**

- **A verdict before any job code.** When the runner in a VM takes a job, kiln pauses that runner, checks that it holds exactly the job it announced, reads the facts about the job from GitLab's API and answers `ok`, `cold` or `refuse` on the VM's console input. `kiln-exec`, the runner's custom executor, waits for that answer in its `prepare` stage, before the job's script, `git clone`, image pull or services; refuse, timeout, an unreadable answer, an answer for a different job id (checked against the runner's own job response, not any job variable) and a second job in the same VM all fail the job once, with no retry. Everything fails closed: a pause or API error, or more than 30 seconds, is a refusal. This gate is a script in the image, not a process-level hold like Gitea's exec gate; it relies on the runner calling it before every stage, and a refused VM is killed after a short grace period.
- **Facts come from the API only.** The host reads the job's `ref`, `tag`, pipeline `source` and project, and for a merge request or branch ref one more lookup. It never reads a `CI_*` variable, which a job's own `variables:` can overwrite, and never anything the guest prints (the job controls its own console).
- **Fork merge requests are refused, including parent-run ones.** A job on `refs/merge-requests/<iid>/...` runs only if the merge request's source and target are both this project; otherwise it is a fork. A pipeline a maintainer runs in the parent project for a fork's merge request (*Run pipeline*) has the same ref and is refused the same way, as is a branch ref that is not a branch of this project, any other `refs/...` ref, and any lookup error. A job kiln would refuse gets no VM of its own.
- **Downstream pipelines are refused.** A multi-project downstream pipeline (source `pipeline`) is refused: its ref is a plain branch whatever the upstream was, but its variables come from a trigger job in another project that kiln never sees.
- **Child pipelines go by ref.** A `parent_pipeline` child is allowed only through the same ref rules: the child of a merge request pipeline keeps the merge request ref, so the fork check applies to it, and a child on a branch belongs to this project's own branch pipeline. A child never saves the cache.
- **Tags and merge trains run cold.** A tag pipeline (the usual release build) and a merge-train ref (which may include a fork's merge request ahead of it) get verdict `cold`: the cache disk is detached before the first step and Docker restarted, so the job runs on the clean base image and can neither read nor write the cache.
- **Cache writes only for trusted pushes.** The overlay is merged only if the job API reports the job as `success` on this VM's own runner, the pipeline source is `push`, the branch is the default branch or a protected branch in `cache_branches`, the VM's console showed exactly one job start, and the host recorded an `ok` verdict for that same job id. Merge request, child, tag, schedule, web, api and every other source discard the overlay.
- **The runner credential is single-job.** The VM receives only a `glrt-` runner token for one project, created with `locked: true` and `run_untagged: false`. The host pauses the runner before the verdict and never unpauses it, so after the gate the runner cannot take a second job (and a job that slips in during the pause is caught because the runner must hold exactly one job); a second job in the VM is also refused by `kiln-exec`. The host deletes the runner whenever the VM ends, and a startup and hourly sweep deletes this install's leftovers (never judged by status). The token is passed through the environment of the runner process, not the command line, and never written to the host's logs or errors. The credential kiln itself uses (below) never enters a VM, QEMU's environment, a guest secret or an error message.
- **Job input is data.** `kiln-exec` quotes every `CUSTOM_ENV_*` value, never evaluates it, validates image and service names and passes them to Docker after `--`. dockerd is not started until the verdict.

**Token power.** kiln's own GitLab credential is more powerful than it looks:

| Credential | What it can do | Mitigation |
|---|---|---|
| kiln's token: `create_runner`, `manage_runner`, `read_api`; the bot user is Maintainer | Create, pause and delete project runners; read project data and job logs. **At Maintainer or Owner, `read_api` makes `GET /projects/:id/variables` return every CI/CD variable value of the project, masked and protected ones included.** GitHub's API never returns secret values. Group and instance variables are not readable by a project member (403). | Use a **dedicated bot user** that is a member of only the served projects, give the token an expiry (the dashboard warns 14 days before), and use it for nothing else. Mark sensitive variables `hidden` (GitLab 17.x and newer), which the API never returns. A split into two tokens (a Maintainer with `create_runner` and `manage_runner` but no `read_api`, and a Reporter with `read_api`) would stop either reading variables; kiln takes one token today and does not offer the split. |
| optional `api` scope | Everything above plus rerun, cancel and run pipeline, and general write access to the projects the bot is in. | Not recommended; kiln shows Rerun, Cancel and Run pipeline only when the token has it. Without it a dashboard cancel still kills the VMs. |
| the `glrt-` runner token in a VM | Take a job for this one project, as a locked runner | Paused before the verdict and never unpaused, deleted when the VM ends. |

The token is stored in `<data>/forges/<id>.token` (mode 0600 in a 0700 directory) or an environment variable, Landlock denies the job VM's QEMU any read of that directory, and the setup UI says all of this next to the token field. Saving a token is tried against GitLab first, audited, and raises a security alert; a forge cannot be moved to another address from the dashboard while keeping its saved token (a hand edit of `config.json` can, since the token file is keyed by the forge id; the box's owner is trusted).

**Residual risks**

- **Variables in a parent-run fork merge request.** If the project allows *Run pipelines in the parent project for merge requests from forks* (`ci_allow_fork_pipelines_to_run_in_parent_project`) and a maintainer clicks Run pipeline, the fork's code runs in your project with its unprotected CI/CD variables, on any runner. kiln refuses the job, but cannot prevent the exposure. A fork's own merge request pipelines run in the fork and never reach kiln's runners. Leave the setting off.
- **A workflow that checks out untrusted content after a trusted trigger** (a job that fetches a merge request's head, or a script that runs what a user supplied through a pipeline variable or a trigger) runs that code in the VM. kiln sees the trigger, not what the script then fetches. The VM is still the isolation boundary, but use `egress: "filtered"` and keep secrets out of such jobs.
- **Your own branches.** Anyone who can push a branch to a served project, or open a same-project merge request, gets a VM, and that job sees the project's unprotected variables (and protected ones on a protected ref), exactly as with any runner. Limit Developer access accordingly.
- **A pending fork job sits until refused.** A pending job kiln will refuse gets no VM, so it stays `pending` in GitLab until a VM for another job takes it and refuses it, or someone cancels it.
- **Cancel latency.** A GitLab runner notices a cancel after up to about a minute. A dashboard cancel therefore kills the pipeline's VMs first, but with only the three recommended scopes GitLab itself refuses the cancel and the pipeline stays running in GitLab until someone cancels it there.
- **A child of a downstream pipeline** looks like a child on a branch. Do not point another project's trigger at a branch of a project kiln serves.
- **`docker:dind` is untested.** Services run privileged inside the VM (the VM is the isolation boundary); the end-to-end test covered `image:` with a normal service (`redis`), not Docker-in-Docker as a service.
- **gitlab.com is untested.** The tier's own limits, rate limits and any hosted-only differences (for instance in runner registration rules) were not tested; the test server was a self-managed CE. kiln backs off on a 429.
- **arm64 is untested for GitLab.** The image carries the arm64 runner and the labels exist (`kiln-arm64`), but no GitLab job has run on an arm64 host.
- **Not tested:** a GitLab server restart or a kiln restart with runners outstanding (the sweep is the safety net).

### Console and lifecycle hardening

Console lines may shape the timeline but cannot rewind state or extend a VM's life:

- each lifecycle line ("Listening for Jobs", "Running job", the result) is accepted once and only forward;
- the hold is granted only after a "Failed" (or "Abandoned") verdict line; a job can forge that or cancel its own hold, but cannot hold a VM that never ran a job, nor take the last free VM slot (at most `max_vms - 1` holds, and the oldest is released when a job is queued);
- lines are capped at 64 KiB (a longer line and its remainder are never parsed) and logs at 64 MiB;
- every VM has a **hard lifetime cap** of idle timeout + job timeout + hold time + 5 minutes, enforced by kiln outside the guest.

### Base image

kiln launches no VM, warm ones included, on a base image baked from an older recipe than the binary expects (`recipe` in `images/base.json`), since such an image may lack the current job hooks (fork refusal, cold release builds). The dashboard shows why, and `auto_rebake` (or Settings › Image) replaces the image. The bake refuses an `actions/runner` release tag that is not `N.N.N`, checks each Node tarball against the release's `SHASUMS256.txt` from nodejs.org before unpacking it, and accepts only plain apt package names in `bake_apt_packages` (no trailing `-` or `+`, which apt reads as remove or install, and no `=` or `/` version pins). The Node checksum guards against a corrupted or swapped tarball, not against nodejs.org itself, since the sums come from the same origin over HTTPS.

### Self-update

kiln installs only releases signed with its release key. Release CI signs each tarball's bytes with an Ed25519 key; the public key is compiled into kiln. The key is a secret of the `release` GitHub Environment, which only `v*` tags can deploy to, and only the `sign` job uses it: that job runs in its own fresh VM after a separate `build` job (where build scripts, proc macros and rustup run) has produced the tarballs, executes no project code, writes the key only to a mode 0600 temporary file removed in the same step, and verifies every signature against the embedded public key before publishing. A tag push runs the workflow file of the tagged commit, so whoever can push a `v*` tag can get a release signed: on this repository a tag ruleset restricts creating, moving and deleting `v*` tags to repository admins. Workflows on pull requests from forks, by any external contributor, need approval before they run (a repository setting), in addition to kiln's own fork refusal. The "tag is on main" check in the workflow guards against mistakes, not against a malicious tagger. Before unpacking anything, kiln verifies the signature, then the tarball's SHA-256, then lists the archive and extracts only the `kiln` binary, which must report the release's version (so an old signed build relabelled as a new release is refused). A compromised release page or `update_repo` setting cannot make kiln run an unsigned binary; what it can do is withhold updates, or (by pointing `update_repo` at a copy of the releases) offer a genuine signed release that is newer than the running one but not the newest. A compromised owner account can publish signed releases. Updates are applied only from the dashboard (or `auto_update`), behind the access guard.

**Who can sign:** the release workflow signs whatever a `v*` tag points at, so anyone who can push such a tag to the repository can produce a signed release, but only of a commit already on `main` (the workflow refuses otherwise) and only when the tag matches `Cargo.toml`'s version. Protect `main` and restrict who can push `v*` tags (a tag ruleset) accordingly. The key reaches only the signing step, which runs after the build and packaging, runs no project code and fetches nothing; the next step checks every signature against the public key in `src/update.rs`, so a wrong key never publishes.

**Key rotation:** a kiln trusts only the key it was built with. Releases signed with a new key are refused by older kilns, so after a rotation install one release by hand; later updates are automatic again. If the private key leaks, rotate it and reinstall by hand everywhere, since every kiln built with the old key would accept a release signed with it.

### Telemetry

kiln reports nothing to its maintainers unless the owner opts in. There are two independent switches, `usage_stats` and `crash_reports`. Both start unset, and unset means off: the dashboard asks once (on the Setup page, or in an Overview banner), and Settings › Privacy changes the choice and shows the usage report exactly as this box would send it now, plus an example crash report. `DO_NOT_TRACK=1` or `KILN_TELEMETRY=0` in kiln's environment turns both off, whatever the config says.

- **Usage** (at most once a day): kiln version, build (glibc or musl), CPU architecture, host thread count and memory in GB, auth mode (token, App or none), the number of GitHub repos, `max_vms`, the default VM size, the number of warm VMs, the egress mode, which features are on (cache, Docker mirror, auto rebake, auto update, debug hold, QEMU confinement), kiln's uptime in hours, and for the last 24 hours the number of jobs, how many passed, job minutes, jobs per VM size, and how many jobs did not pass by cause (failed, cancelled, timeout, killed by a user or by kiln shutting down, ran out of memory, lost, ended without a result, refused by policy, refused because kiln or the forge failed closed, other), all counts (taken from the last 200 jobs kiln keeps records of).
- **Crash** (when kiln panics): version, build, architecture, the panic's location in kiln's source code (`src/vm.rs:123:45`; a dependency's location starts at its crate directory in cargo's registry, the standard library's at `core/` and the like, and any other location, such as generated code or a path, vendored or workspace dependency of a self-built binary, is sent as `other`, without even its file name), the thread kind, uptime and time. **The panic message is not sent**, since it can quote a repo name, a path or a login. Only these fields are sent, whatever a crash file on disk holds. Panics are written to `<data>/crash/` (at most 20 waiting) only while `crash_reports` is on, and sent hourly from 10 minutes after start, so a crash loop sends nothing.
- **Never sent:** repo, owner, user or org names, the runner label, host names, IPs, tailnet names, file paths on this box, tokens or keys, job names, logs or workflow contents, and config values beyond those listed above.
- Reports carry a random install id (`<data>/telemetry_id`) so one box's reports can be grouped. It is not derived from anything on the box, is created at the first send (looking at Settings › Privacy does not create it), and is deleted as soon as both switches are off, so opting in again starts a new id. Turning crash reports off likewise deletes any waiting crash files at once.
- kiln sends the reports itself over HTTPS (no redirects followed, 20-second timeout) to `https://kiln-telemetry-api.vercel.app/v1`, a small service the maintainers run on Vercel with a Postgres database (Neon). The browser never contacts it: the dashboard's CSP stays `connect-src 'self'`. The service accepts only the fields above, each typed and range-checked, stores no IP address or other request metadata, never logs report bodies, and deletes reports after 400 days; Vercel, as its host, sees the connection and keeps request logs. A send that fails on the network or the server is retried the next hour; a report the service refuses is dropped, not resent. Neither ever affects jobs. `KILN_TELEMETRY_URL` can point kiln at a test receiver; if it is set but not `https://`, nothing is sent (never the built-in address).

### Docker mirror

The mirror listens on host loopback only and is a pull-only proxy of public Docker Hub images. It holds no credentials and cannot be pushed to. The registry binary it runs is pinned by version and SHA-256, and a different download is refused.

### Notifications

Outbound alerts must not become a way to reach into the box's network. Destination URLs must be https, without credentials, and Slack and Discord are pinned to their own hosts. The address check runs inside the DNS resolver, so the connection goes to exactly the addresses that were checked (there is no rebinding gap); IP-literal URLs are checked when saved and again when sent, and every stored URL is re-checked against the URL rules (https, host pinning, address ranges) on every send, so a hand-edited `notify.json` cannot get past them. Loopback, LAN, link-local, IPv6 site-local `fec0::/10`, cloud metadata, documentation (`2001:db8::/32`, `3fff::/20`), multicast and reserved ranges are always refused, with IPv6 mapped, compatible, NAT64 and 6to4 forms judged by the IPv4 inside, and the other IPv6 translation prefixes (local-use NAT64 `64:ff9b:1::/48`, SIIT `::ffff:0:0:0/96`, Teredo `2001::/32`) and discard `100::/64` always refused; CGNAT `100.64.0.0/10` and IPv6 unique-local `fc00::/7` are refused unless the destination is marked "on my tailnet", which then allows only `100.64.0.0/10` and `fd7a:115c:a1e0::/48`. The client follows no redirects, ignores proxy environment variables, has a 5 s connect and 10 s total timeout, and reads at most 4 KiB of any response.

`notify.json` is mode 0600. URLs and ntfy tokens are write-only: they never appear in API responses, logs, audit notes or job VMs. A signing secret is returned once to the admin who caused it (create, rotate, or a change of kind or URL origin) and never again, and is otherwise kept out of the same places. An edit that moves a URL to another origin (scheme, host or port) drops the stored ntfy token unless a new one is supplied, and replaces a generic destination's signing secret, so a changed URL cannot carry an existing credential to a new party. Text from repos (names of repos, jobs, branches, workflows, actors) is cleaned of control and invisible characters, capped, and escaped per target: Slack `<!channel>` and `<@…>` become inert text with link previews off, Discord sends `allowed_mentions: {parse: []}`, and ntfy gets repo text only in the body, never in headers. Slack, Discord and ntfy repo text is de-linked, so only job links on the forge's own origin are clickable (`https://github.com/`, or a GitLab or Gitea server's own address, plain `http://` included for an internal forge). Generic payloads are signed with [Standard Webhooks](https://www.standardwebhooks.com/) HMAC-SHA256 signatures; receivers should reject timestamps more than 5 minutes old. Each destination is limited to 30 messages a minute, and adding, changing, removing or re-keying a destination is announced to every destination, including the one removed, queued before the old destination's worker is retired, so a removed destination still hears about it. See [Notifications](docs/configuration.md#notifications).

### Debug SSH

sshd does not run during jobs. Held VMs accept keys from `debug_ssh_keys` only (no passwords, no root login), on a port bound to the box's tailnet address or loopback, with host key fingerprints printed for you to compare.

## Known residual risks

kiln is honest about these:

- **Open egress is the default.** With `egress: "open"`, a job has full outbound access including your LAN and your tailnet (it appears to come from the box), and, through QEMU's `10.0.2.2`, **every service listening on the host's loopback** (databases, dev servers, local admin UIs): QEMU's user networking has no switch to turn that off. That is fine for your own private repos and not for untrusted code or a box that runs other services. Filtered mode blocks all of it except the Docker mirror; it is opt-in until it has been verified on more hosts.
- **DNS exfiltration in filtered mode.** DNS goes through the host's resolver, so a job can leak data in DNS queries. DNS is not filtered.
- **IPv6 is disabled, not filtered.**
- **macOS has no filtered egress and no VMM confinement.** On Apple Silicon (experimental) jobs always have open egress; kiln refuses `egress: "filtered"` there. QEMU also runs without seccomp and Landlock (see [VMM confinement](#vmm-confinement)). Do not run untrusted code on a Mac kiln.
- **The denylist covers private ranges only.** Public addresses that the host can reach are not blocked. Notably, if your router hairpins its WAN address, a job could reach services you forwarded from the Internet. Keep Tailscale subnet-route acceptance off on this host, since routed subnets would also be reachable.
- **Without `rootlessctl`, the debug SSH port is open for the whole VM life in filtered mode.** The port is published statically at launch rather than at hold time. Nothing listens on it by default, but a job is root and could start a listener. Install `rootlesskit` with `rootlessctl` to publish it only at hold time.
- **The Docker mirror's `/v2/_catalog` and other reads are visible to every job** and shared between repos. It only caches public images, so this is acceptable, but jobs can learn what other jobs pulled.
- **The cache can be poisoned by a compromised default branch or cache branch.** The trust rule stops PRs and other branches, not code already merged into a writer branch. Only list branches in `cache_branches` that are as protected as the default.
- **The base image gives `runner` passwordless sudo,** and bake VMs always use open networking.
- **Local file secrets.** The GitHub token, other forges' tokens (`<data>/forges/`, readable only by the kiln user and denied to QEMU by Landlock) and dashboard key are plain files readable by the kiln user.
- **One host.** There is no tenant separation between repos beyond VM and cache-disk isolation.
- **Nested virtualization is on.** Guests get `-cpu host` and may use KVM themselves (Android emulators, VM tests), which exposes the host's nested-virtualization code to jobs.
- **Secrets in cached paths persist.** Apart from the login tokens kiln scrubs, anything a trusted job writes under a cached directory (including Docker images built with secrets in their layers) is visible to later jobs of the repo, pull requests included, exactly as with `actions/cache`.
- **One release key.** Self-update trusts a single Ed25519 key; losing it means installing one release by hand on every box, and a leaked key must be rotated the same way. Releases carry no signed expiry, so a mirror can withhold updates (see [Self-update](#self-update)).
- **Landlock depends on the kernel.** Without it (Linux older than 5.13, or `landlock` missing from `lsm=`), QEMU is limited by seccomp only.
- **macOS has no VMM confinement.** QEMU on Apple Silicon runs without seccomp and without Landlock, so an escape from the guest reaches the kiln user's files, tokens included.

## Recommendations

- **Never let fork pull requests reach kiln.** kiln refuses them itself (see [Fork pull requests](#fork-pull-requests)); as a second layer, for a public repo guard every `pull_request` job (kiln's own workflows and the `kiln-hello.yml` it generates already do):

```yaml
jobs:
  test:
    # Never run pull requests from forks on self-hosted hardware.
    if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository
    runs-on: [self-hosted, kiln]
```

  Also keep GitHub's "Require approval for all outside collaborators" setting on (Settings › Actions › General). Workflows that check out a pull request's head from an `issue_comment`, `repository_dispatch` or `workflow_dispatch` trigger must not use kiln on a public repo: kiln cannot tell (see [Fork pull requests](#fork-pull-requests)).

- Set `egress` to `filtered` before running untrusted pull requests, such as ones from forks, and check Diagnostics shows "filtered egress" passing. Also consider requiring approval for workflows from outside contributors in the repository's GitHub settings.
- Prefer a GitHub App (Settings › Forges › Create GitHub App, see [docs/configuration.md](docs/configuration.md#github-app)): only its private key is stored, its tokens expire after an hour, and it never gets write access to code. Otherwise,
- use a fine-grained token with only the repos you serve and the permissions listed in [docs/configuration.md](docs/configuration.md#github-token): *Administration: write*, *Actions: read and write* and *Contents: read*. Add *Contents* and *Workflows* write only while you use the hello PR.
- On GitLab, use a dedicated bot user in only the served projects, leave *Run pipelines in the parent project for merge requests from forks* off, mark sensitive variables `hidden` and protected, and keep the optional `api` scope off (see [GitLab](#gitlab)).
- Keep `allowed_users` empty (owner only) or minimal, and do not share the box's node to other tailnets.
- Keep the host, QEMU and Tailscale updated, and let `auto_rebake` keep the guest and runner current.
- Do not put secrets on the CI box that a job in an open-egress VM could reach over the LAN.
- Release debug holds when done; a held VM keeps a login path open until it expires.

## Reporting a vulnerability

Please do not open a public issue for a vulnerability. Report it privately through GitHub's private vulnerability reporting: on the repository, go to **Security › Report a vulnerability**. Include what you found, how to reproduce it and the kiln version (`kiln --version`). There is no formal response-time guarantee, but reports will be looked at promptly.

Releases are signed (see [Self-update](#self-update)), and on the public repository each release tarball also has a GitHub build provenance attestation: `gh attestation verify kiln-X.Y.Z-x86_64-linux.tar.gz --repo Bunty9/kiln`. CI checks dependencies against the RustSec advisory database, licenses and sources with `cargo deny` on every change.
