# Changelog

All notable changes to kiln are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Local Actions cache (off by default while it soaks).** With `gha_cache` on (Settings › Cache, or `"gha_cache": true`; applies to the next job, no restart), `actions/cache`, the `setup-*` caches and `Swatinem/rust-cache` on GitHub repos are saved and restored on the kiln host instead of GitHub, with no workflow change. Only a successful push to the default branch (or a cache branch) writes the shared cache, pull requests read it but cannot change it, and release and tag builds skip it; what each VM calls is decided from the kernel, never from the job. Settings › Cache shows its size and each repo's entries (Clear now clears both caches), the job page shows what a job restored and saved and whether it was promoted, `kiln doctor` has an `actions cache` row, and usage statistics report whether it is on (`features.gha_cache`). Linux hosts only; Gitea and GitLab are not served yet, and protobuf clients such as sccache go to GitHub. **Rebake the image to use it:** the bake now patches the Actions runner (an image baked earlier keeps using GitHub's cache, and a runner kiln cannot patch is left alone and reported as unsupported).
- **Notification dashboard links.** The "Include dashboard link" option on a notification destination now works: a job message links to the job's page in the dashboard when Serve over HTTPS is on (a `.ts.net` address only; no link otherwise). kiln caches the address from the serve config it already reads and never runs `tailscale` while sending.
- **A VM that runs out of memory takes only itself.** Each job VM runs in its own transient systemd scope (`kiln-vm-<id>.scope`, memory-capped at its RAM plus 1.5 GB) on Linux hosts with `systemd-run`, so systemd-oomd or the kernel OOM killer takes one VM instead of the whole `kiln.service` with every running job. A VM killed that way ends as killed with "likely out of memory" and counts as `oom` in `fail_causes_24h`. Without systemd (macOS, containers) nothing changes. If scopes are unavailable the probe is retried every 5 minutes, and `kiln doctor` shows `vm cgroups` as a warning with the reason. The shipped unit stops leftover scopes on stop, and kiln stops them at start; reinstall the unit to get the former (kiln does the latter regardless). Only one `kiln serve` can run per data directory (a lock on `serve.lock`), so a second one started by hand exits with "another kiln serve is running on this data directory" instead of stopping the live service's VM scopes.
- **Launches hold while the host stalls on memory.** Linux PSI `some avg10` above 20% (`/proc/pressure/memory`) shows "host memory pressure ... holding launches" on the Overview and in `kiln doctor`, and launches resume by themselves.

### Changed

- **Usage statistics say why jobs did not pass.** The opt-in daily report gains `fail_causes_24h`: a count of the last 24 hours' non-passing jobs by cause (`failed`, `cancelled`, `timeout`, `killed`, `oom`, `lost`, `no_result`, `refused_policy`, `refused_failure`, `other`), from kiln's own VM records. Counts only, no names, URLs or messages; `GET /api/telemetry` shows the exact report.
- **Overview: the host graphs hover together.** Hovering (or tapping, or arrowing along) either the CPU or the Memory chart draws the crosshair on both at the same moment and shows a popup on each, with that chart's own values and unit (cores, GB). The popups sit beside the line and move above and below their charts when they would touch. Leaving the charts clears both.
- **Overview: Recent jobs have a hover card.** Rest the pointer on a row (mouse and trackpad only) or focus it with the keyboard and a card shows the job's full branch or PR, title, commit, event, workflow, outcome, size, warm or cold start, cache outcome, refusal reason, the timeline with its durations and clock times, and peak CPU and memory when the host graph has samples. The card stays open under the pointer so text can be copied, closes on Escape, scroll or leaving, and never shows on touch screens, where a tap still opens the job.
- **Event icons.** Recent jobs, the Jobs list, the job page and a repo's runs show a small coloured icon for what started the run: pull or merge request, merge group or merge train, branch push, tag or release, manual run, schedule, a workflow or pipeline triggered by another, and refused fork pull requests. Each has a light and a dark colour token (`--ev-*`, at least 4:1 on the card) and a name for screen readers.
- **Page titles.** The browser tab now names the page ("Overview · kiln", "acme/demo · kiln"), keeping the running count and failure marker in front.
- **Host graph colours.** With more than six VMs the Overview graphs no longer repeat colours: each further set of six uses lighter, then darker, shades of the same hues.
- Dependencies: base64 0.22 to 0.23, serde_json 1.0.151 to 1.0.154 (#105).
- Offline banner is announced to screen readers at once, and the two navigation landmarks have distinct names. Docs: `app_accounts` has a settings row, and the account rule for the GitHub App is stated correctly; `/api/host` and `/api/analytics` are in the route table.

### Fixed

- **Dashboard polish.** The Actions cache shows "0 MB" for an empty cache, hides "Using X of Y GB" while the switch is off, and the Clear confirmation mentions the Actions cache. A Diagnostics check that passes with a warning shows an amber badge. On a 320px phone the repo page's run rows give the title room (buttons wrap under it) and long workflow paths wrap. On touch screens, chips, buttons, summaries, `?` buttons and links are at least 32px tall.
- The Docker mirror no longer logs a failed trace export every few seconds.
- **VM launches no longer fail with `Failed to initialize io_uring: Cannot allocate memory`** when other programs of the same user (editors and agent tools) hold io_uring memory. kiln lowers its own soft locked-memory limit (`RLIMIT_MEMLOCK`) to 0 at start, which QEMU and `qemu-img` inherit, so they use threads instead of exiting. There is nothing to configure: the unit no longer sets `LimitMEMLOCK`, and `kiln doctor`'s `io_uring` check passes. As a backstop, if a launch still hits the error, kiln pauses launches with a doubling delay (1 minute up to 15), keeps only the first failed VM instead of creating one every minute, probes with one launch, and shows the cause on the Overview. `kiln doctor` has new `io_uring` and `memory pressure` checks.
- **Time stamps with a zone offset parse correctly** (`+05:30`). A Gitea server not on UTC no longer shifts job wait times by hours, and an unreadable Gitea time no longer shows 1970. (Fractional seconds were already ignored.)
- **Repo page on a phone: a failed run's buttons ran off the screen.** Rerun failed, Rerun and Open now wrap onto their own line.

- **Settings › Notifications: a typed destination URL survived only until the next refresh.** An open Add or Edit form is no longer rebuilt when the settings change underneath it.

- **Overview: the burning card edges show on phones.** Running cards showed a flat card, with no burnt edge and no still frame, on an installed Android app and some browsers. The edge sprite sheets were 5248 px tall, over the 4096 px texture limit of many phone GPUs and WebViews, and the browser dropped the image. Each edge sheet is now two files of 20 frames, 2688 px tall, and the animation switches file halfway through the loop. The frames, resolution, speed and encoder settings are unchanged (the same recorder re-run; the decoded pixels differ from the old sheets only by WebP noise).
- **The dashboard key is no longer replaced on a read error.** A permission or I/O error reading `dashboard.key` at start now stops kiln with the reason; the key is regenerated only when the file is missing or too short.
- **A bad update rolls back even when the boot count can't be saved.** If the data directory is full or read-only, kiln now rolls back to `kiln.prev` at once instead of crash-looping the new build forever.
- **A panic in the scheduler no longer leaves kiln serving but idle.** If the scheduler task ends while kiln is not stopping, kiln logs an error, shuts down (no grace drain) and exits non-zero, so systemd restarts it (and the startup cleanup runs). Before, nothing would ever launch, poll or clean up again while the dashboard stayed up.
- **Pre-1970 clock.** A host clock set before 1970 no longer panics; time reads as 0.
- **Corrupt usage ledger.** An unreadable `usage.json` or `usage-other.json` now logs a warning instead of silently showing zero usage.
- **Clear cache** reports an error if the parked cache overlay cannot be removed, instead of clearing the cache and leaving the stale overlay to be merged into the next one.
- **Hover hints in dark mode.** The small hints that appear when you hover or focus badges, stats and times were a bright box with dark text in dark mode. They now use the same surface, text, ring and shadow as the `?` popovers in both themes. (The browser's own `title` tooltips are drawn by the browser or OS and cannot be styled; the dashboard sets `color-scheme` per theme, so the page's form controls and scrollbars follow the theme, and kiln uses its own hint for its text.)

### Security

- rustls-webpki 0.103.16 and webpki-roots 1.0.11 stop trusting the distrusted emSign intermediates (RUSTSEC-2026-0382, RUSTSEC-2026-0381); tokio is 1.54.1 for the `AsyncFd` I/O-safety advisory (RUSTSEC-2026-0386, kiln does not build `AsyncFd` from raw descriptors). libc is 0.2.191.

- rustls is 0.23.46 (was 0.23.45), fixing RUSTSEC-2026-0346 and three other rustls advisories. kiln was not exposed to most of them (no custom session store, no ECH, no brotli certificate compression); the remaining one could downgrade later TLS connections from hybrid post-quantum to classical key exchange.

## [0.2.6] - 2026-10-14

Multi-forge release: kiln now serves GitLab and Gitea next to GitHub, runs on Apple Silicon and arm64 Linux hosts, and ships signed releases for Linux x86_64 and arm64 and for macOS arm64. Hosts self-heal at boot after a restart, and the dashboard has a refresh with full help for every feature. The base image recipe changed (`RECIPE` is 14), so every install rebakes once on upgrade (automatic with `auto_rebake`; until then no VM launches).

### Added

- **Analytics covers 30 days of job history.** Settings › Analytics used to be computed from the newest 100 VM records, so on a busy box older days showed as hatched. kiln now keeps `jobs.jsonl` in its data directory: one compact line per finished job (repo, job name, size, outcome, timings; no URLs, logs or commit text), kept 90 days and at most 50,000 lines, mode 0600. The first start with this version fills it from every VM record on disk; days before that stay hatched, and the usage ledger still counts them. New `GET /api/analytics?days=1|7|30&repo=&cpus=` (behind the dashboard key like the rest of `/api/`); `/api/state` is unchanged. Older kiln versions ignore the new file.
- **`job.refused` alert.** A job the verdict gate refuses because kiln or the forge failed closed (verdict timed out, forge API error, pause error, a held-job mismatch) now alerts destinations with job alerts on; policy refusals (fork, `workflow_run`, GitLab `pipeline` source, another project's job) stay silent. The payload is the `job` object with `outcome: "refused"`, `class: "failure"` and `reason`; existing payloads are unchanged.
- **GitLab support.** kiln serves GitLab projects on gitlab.com and self-managed GitLab (16.0 or newer accepted, 17 or newer recommended) next to GitHub. Tested end to end against GitLab CE 19.4.1: plain, `image:`, `services:` and tagged jobs, a fork merge request, child and downstream pipelines, dashboard cancel and runner cleanup.
  - **Setup.** A bot user as Maintainer on only the served projects and a token with `create_runner`, `manage_runner` and `read_api`. A Maintainer's `read_api` token can read the project's CI/CD variables, so use a dedicated bot (documented as "token power" in the wizard, the Use GitLab guide, docs/configuration.md and SECURITY.md). Settings › Forges tries the token before saving it (rejected, expired, a missing scope named, a role below Maintainer per project); `kiln doctor` checks the same and names the three causes of GitLab's runner-creation 403. Rerun, Cancel and Run pipeline need the optional `api` scope and appear only when the token has it.
  - **Jobs.** A job asks for kiln with `tags: [kiln]` (or `kiln-2cpu` ... `kiln-16cpu`; `kiln-arm64...` on an arm64 host). For each job kiln creates a locked project runner, boots a fresh VM and hands it that one `glrt-` token. The image's pinned GitLab Runner 19.4.1 runs one job through a custom executor, `kiln-exec`, which runs plain jobs in the VM and `image:`/`services:` jobs in Docker inside it. Artifacts upload as usual.
  - **Verdict gate.** Before any job code runs, the host pauses the runner, checks it holds exactly the announced job and decides from GitLab's API alone (never a `CI_*` variable). Fork merge requests (including ones run in the parent project), multi-project downstream pipelines and anything unclassifiable are refused; tags and merge-train refs run cold; child pipelines go by their ref and never save the cache. A refused job gets no VM of its own. The runner is never unpaused and is deleted when the VM ends; a sweep at startup and hourly deletes leftovers. A dashboard cancel kills the pipeline's VMs first, then asks GitLab (needs `api`).
  - **Cache.** The repo cache disk works as on GitHub and is saved only after a `push` pipeline on the default branch or a protected `cache_branches` branch whose job the API reports as `success` on the VM's own runner, with one job start and a recorded `ok` verdict.
- **Gitea support.** kiln serves Gitea repos (1.25 or newer, 1.26.3 recommended). Tested end to end against Gitea 28.1.0 with gitea-runner 5.0.0: plain and JavaScript-action jobs, `container:` and `services:`, tags, fork pull requests (new and repeat contributor), `pull_request_target`, `workflow_run`, a cache poisoning attempt, rerun, cancel, filtered egress and runner cleanup.
  - **Setup.** A dedicated service account that is the repo's Owner (Gitea gives the runner registration token only to an Owner) with a token that has `write:repository` and `read:user`. That account can change or delete the repo, so use one that owns only the served repos. Settings › Forges tries the token before saving it and shows the account's role per repo; `kiln doctor` runs the same check.
  - **Exec gate.** `kiln-job` starts `gitea-runner daemon --once` under `kiln-gate`, a root fanotify gate that holds every exec of the runner's processes until the host's verdict. Two gate processes watch independently; if one dies the runner's processes are killed and kiln kills the VM. `vm.memfd_noexec=2` is set for the job and dockerd stays down until the verdict. The verdict binds the job in progress on this VM's own runner. Fork pull requests, `pull_request_target` from a fork and every `workflow_run` are refused before any job code runs; tags run cold.
  - **Cache.** The repo cache disk works as on GitHub with the same trust rule. Gitea's own `actions/cache` does not persist (its server lives on the VM's disk).
  - **Launching.** A fork job queued on a Gitea repo shows a dashboard banner; each such job can cost one VM, which the gate refuses and kills. Require approval for fork pull requests on the forge.
- **Apple Silicon and arm64 releases.** On macOS kiln runs native linux/arm64 VMs with QEMU and Hypervisor.framework (experimental, untested on a real Mac), advertising `ARM64` runners labelled `<label>-arm64` and `<label>-arm64-<N>cpu`, never the plain label. aarch64 Linux hosts with KVM work the same way. Adds a launchd LaunchAgent (`deploy/kiln.plist`), a `macos` CI workflow and `scripts/macos-smoke.sh`; no filtered egress and no Docker mirror on macOS. See [docs/apple-silicon.md](docs/apple-silicon.md). Every release now also ships `kiln-X.Y.Z-aarch64-linux.tar.gz` (glibc 2.39+), `kiln-X.Y.Z-aarch64-linux-musl.tar.gz` (static) and `kiln-X.Y.Z-aarch64-macos.tar.gz` (ad-hoc signed by the linker, not notarized), signed with the same Ed25519 key as the x86_64 tarballs. kiln updates itself from the tarball for its own OS, CPU and libc, and refuses to update on a platform with no build (Intel Mac, other CPUs).
- **Forges in the dashboard.** Settings › Forges (formerly Settings › GitHub) has one card set per forge: add, test and remove a GitLab or Gitea forge (address, network, projects, token), with the token tried before it is saved and never shown again. The setup wizard's first step is "Connect a forge" for GitHub, GitLab or Gitea. The Repos page lists the repos of every forge with a forge badge once more than GitHub is served, with runs, workflows, Rerun, Cancel and Run following each forge's capabilities and CI snippets per forge. Overview banners name the forge for a missing or rejected token, a rate limit, an unreachable forge, a token near expiry, missing GitLab scopes, a refused runner registration and a fork pull request waiting on Gitea. Job pages name the forge in the log tab. The dashboard talks to a forge-neutral API returning kiln's own JSON (`/api/forges`, `/api/runs`, `/api/jobs/{id}/log`, `/api/workflows`, rerun, cancel and dispatch); the old `/api/gh/*` passthrough is removed.
- **Forge-aware notifications and usage.** Job payloads gain `forge` (id) and `forge_kind` (`github`, `gitlab`, `gitea`), signed bodies still verify, and chat messages add the forge name; a link is sent only if it is on that job's own forge. `notify_rules` accept `<forge-id>:<path>` repos and, for GitLab, the pipeline name (`pipeline`) or `*` as the workflow. GitLab and Gitea job minutes go to their own ledger, `usage-other.json`, and are listed unpriced on the Saved card and in Analytics; `usage.json` holds GitHub jobs only, so a rollback reads it as before.
- **Filtered egress with a private forge.** A job VM of a forge with `network: internal` gets one extra accept for that forge's `ip:port` and nothing else private. The forge `url` must be an IPv4 literal; loopback, host-own, link-local, IPv6, slirp's `10.0.2.0/24` and port 25 are refused at launch. Opening an address opens every site behind it. The egress probe checks each configured forge's own origin.
- **Base image.** Carries the GitLab runner (19.4.1) and the Gitea runner (5.0.0), pinned by version and SHA-256 per architecture and verified during the bake, plus `kiln-exec`, `kiln-gate` and image checks (Docker, `vm.memfd_noexec`, kernel fanotify permission events, no sshd or linger for `runner`; the bake fails if one fails). The image counts as stale by age or a newer `actions/runner` only when a GitHub repo is served.
- `forges` in `config.json` (id, kind, url, credential, network, repos), documented in docs/configuration.md; a forge token comes from `<data>/forges/<id>.token` or `KILN_FORGE_<ID>_TOKEN`.

- `/api/state` gains `platform: {os, arch}` (Rust's `std::env::consts` names), so the dashboard can hide what the host refuses. A job the verdict gate refused is documented as `verdict: ["refuse", id]` plus a `refused:` note, and sends no `job.failed` alert whatever the reason (a fail-closed refusal sends `job.refused`).
- **Dashboard help for every feature (HELP).** Help now has 21 guides in five groups, a search box, a "Related" footer on each guide and a banner-by-banner troubleshooting table. New guides cover forges (with a GitHub, GitLab and Gitea comparison), fork pull requests and refused jobs (every refusal reason, and which are policy and which are kiln failing closed), release builds and cache trust per forge, private forges and the job network, Apple Silicon, updates, restarts and self-heal (including the "starting: waiting for the network" states after a reboot), notification rules per forge, usage and savings by forge, and warm VMs. The Getting started and Move guides show the GitHub, GitLab and Gitea form of a job as tabs. Sixteen new or extended `?` popovers (GitHub credential, forges, refused jobs, cold runs, internal networks, Apple Silicon, updates, restarts, workflow rules, alert types, the warm VM budget, timeouts, cache branches and others) each link to their guide, one-time tips cover setup, refused and held jobs, arm64 boxes, mixed-forge boxes, updates and Help, and empty Cache, Notifications, Repos, Jobs and Analytics pages say what to do first. The Debugging page warns when a hold is set with no SSH key, and Capacity shows how many slots warm VMs may hold. `dashboard.check.js` now fails if a `?` has no help entry, a guide link does not resolve, or a tip is never shown.

### Changed

- **Overview: running VM cards burn at the edges like paper while a job runs** (a still frame with reduced motion). The effect is pre-recorded (`scripts/burn/record.py`) and played back from 1 MB of embedded WebP sprite sheets, so a burning card costs almost no CPU.
- **macOS plist `ExitTimeOut` is 600** (was 30), matching the systemd unit's `TimeoutStopSec`, so launchd no longer SIGKILLs kiln inside the default 25 s stop grace plus cleanup. Docs now say plainly that on macOS QEMU runs without seccomp and Landlock.
- The guest reads kiln's secrets (JIT config, runner credentials, debug SSH keys) through one helper: SMBIOS strings on x86_64 (command line unchanged), fw_cfg files on arm64. The console and step-log devices are per architecture.
- **Docker starts on first use.** dockerd is no longer started at boot on any forge; `docker.socket` activates it on GitHub. There the job-started hook decides cold or warm before the first container step; GitLab and Gitea start it only after their verdict, and a cold run only after the cache disk is detached.
- A runner registration failure on a forge other than GitHub (Gitea: no answer or a 5xx) backs off that forge's launches the way GitHub's does. Recycling a Gitea runner after a security-settings change cancels the job it holds on Gitea 28+.
- QEMU and its helpers (rootlesskit, slirp4netns) start with a cleared environment and inherit only `PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR`, `XDG_RUNTIME_DIR` and `RUST_LOG`.
- A forge `url` must be plain ASCII without quotes, backslashes, whitespace or credentials, https (http only with `network: internal`), in canonical form (lowercase host, no default port, no `0x7f.1`-style or percent-encoded hosts), and not a loopback, host-own or link-local address.
- A settings save (`POST /api/config`) can no longer add or remove a forge or change an existing forge's address, kind, token source or network; use Settings › Forges (or remove the forge and add it again). Two entries for one server are refused.
- A job log over 16 MiB shows its first 16 MiB with a note, instead of an error.
- The Repos tab's cache Clear works for GitLab and Gitea repos.

### Fixed

- **Doctor no longer reports a stray qemu while a job runs.** The check counted rootlesskit and its helper (which carry QEMU's command line) as QEMU, three processes per VM, so every running job showed "1 health check failing". It now counts only `qemu-system*` processes and matches each to an active VM by its `vms/<id>/q/` path. The dashboard also re-runs the checks (at most every 20 s) when the set of active VMs changes, so a cleared failure stops showing as a banner.
- **Dashboard polish.** The Kill VM dialog says what happens (the VM stops now; the forge marks the job failed after its runner times out; a VM killed while booting leaves the job queued). An unknown address shows "Page not found" instead of the Overview. The `?` help buttons are 24 px on phones. Guide search snippets no longer repeat the guide title. Add forge shows a server-side error next to the field as well as in the toast.

- **The dashboard no longer throws "Cannot read properties of null (reading '_h')".** A poll that landed after you navigated away from the Overview page tried to render into elements that were gone; it now skips them.
- **An open dashboard tab reloads when kiln's build changes, not only its version.** A same-version redeploy (dev builds, a reinstall) used to leave the tab running old JavaScript that misread new API shapes, such as grey VM bands in the host graphs. `/api/state` now carries a `build` id (a hash of the version and the embedded dashboard); a tab whose page differs reloads once, and the offline cache is keyed by it too.
- **Host graphs end a VM's band when the VM ends.** The colored band (and its line) no longer runs on to "now" after a VM is destroyed: it stops at its last sample with a clean edge, and the legend lists only the VMs in the chosen window. Each new VM takes the next of six rotating colors (blue, vermillion, green, gold, purple, pink), so consecutive jobs differ even with two slots.
- **kiln is healthy after a reboot without a restart.** It used to start before the network, and several things failed once and stayed failed. Now each retries with backoff until the network, DNS and tailscaled are up, and for the first 3 minutes the dashboard and `kiln doctor` say "starting: waiting for the network" instead of failing (no alerts either); after that a check that still fails shows its real error. See [After a reboot](docs/configuration.md#after-a-reboot).
  - **Docker mirror.** The registry crashed (exit status 2) when Docker Hub did not resolve as it started, and was restarted with a growing delay. It now starts only once `registry-1.docker.io` resolves, and counts as running once it answers (the egress probe could meet it half-started).
  - **Filtered egress.** The probe is no longer run in a namespace while DNS is down (each target cost an 8 s timeout); it retries every 5 s then.
  - **Leftover runners.** The startup sweep ran once, and not at all for an App whose repos were not discovered yet, so a boot with a slow network left the previous run's runners registered. The runners of lost VMs are now deleted by id on every forge, and the sweep is retried (and covers repos discovered late) without touching VMs that are booting. A reboot also deletes every VM's disks, JIT secret files and rootlesskit state, and `rk/` and `egress-check/` leftovers.
  - **Retries.** App discovery retries after 5 s (not 30 s or 5 minutes); a failed update check after 5 minutes (not 6 hours); a failed auto-rebake after 5 minutes, doubling (not 6 hours); no rebake starts before the network is up.
  - **Listen address.** A `listen` on a tailnet address that tailscaled assigns late no longer leaves kiln on loopback until a restart: it serves on the address as soon as it binds. An unreadable `tailscale serve status` is rechecked after 5 s, not 60, and is no longer logged as an unsafe config.
  - **systemd unit.** `deploy/kiln.service` waits up to 30 s for a default route before starting kiln (reinstall the unit to get it; kiln copes without).
- GitLab jobs could not start in a VM: the executor's state directory `/run/kiln-exec` is now created for the `runner` user.
- Gitea jobs ended as `failed` ("runner exited without a result") and never saved the cache even when they passed: the result now comes from Gitea's job API for the VM's own runner.
- The dashboard refreshes its forge list with every state poll and retries after a failed load, so a restart or a newly installed App repo no longer leaves Rerun, Cancel and the forge links missing until a reload.
- A cache overlay is committed only when the VM's own console showed exactly one job start and a job id is bound; a second start, no start or an unbound job discards it.
- `forges[]` entries keep fields this version does not know (a newer kiln's), so a downgrade still starts. Remove `notify_rules` that name a `<forge-id>:<path>` repo before downgrading: an older kiln refuses them.
- Notification job links are checked against the forge origins when a message is built. Branch links no longer accept `.` or `..` segments.
- `kiln doctor` no longer reports "not enough for all slots at once" whenever every slot is busy: it counted the memory held by kiln's own running VMs twice.
- Filtered egress no longer stays "unavailable" after kiln starts before the network is up: a failing probe is retried after 5 s, doubling up to every 2 minutes, and a save that changes `egress`, `listen` or `docker_mirror` while filtered re-probes at once. `deploy/kiln.service` drops `After=network-online.target`, which a user unit cannot order against (#44).
- On a phone, swiping right to left between the bottom tabs no longer makes the tab bar jump or the page scroll glitch. The slide-in moved the whole page 32px past the right edge for a moment, which widened the page; it now moves only the page's content, which stays clipped.
- **Dashboard audit fixes (UI-FIX).** The setup wizard was blank on the GitHub path (it failed while drawing its GitLab/Gitea branch); `dashboard.check.js` now mounts every setup path and every Settings group, so that class of bug fails CI. A job the verdict gate refused on purpose (a fork pull request, a `workflow_run`, a job kiln cannot classify) now has its own `refused` status: its own badge, a neutral note with the reason, no red timeline segment, and it no longer counts in Failed in 24h or Recent failures, flips the tab title or sends a `job.failed` alert. Overview shows at most three alerts (blocking first, then needs-action, then FYI; "N more alerts" holds the rest), merges the problems of one forge into one card and lets you put off the FYI ones with Later. A repo is shown as a forge chip and its clean path everywhere (jobs, tiles, job title, cache list, analytics, rule and filter menus); GitLab and Gitea no longer show the "preview, jobs will not run" note when launches are on; Capacity, Timeouts, the status line and the API counter no longer assume GitHub. On macOS, Filtered egress and the Docker mirror are shown as unavailable and the update flavor reads "macOS build". Releasing a held VM, cancelling a run, stopping a project and forgetting the dashboard key now ask first. Settings groups say how they save (instantly, or with Save), the tip is per group, Reset tips moved to Appearance, the Network page has one "What jobs can reach" card and a plain "Not checked" line, and Forges shows a summary of all forges, folds healthy cards, checks projects on load and leads with the GitHub App in the wizard and in Settings, as the docs recommend.
- **Usage ledger counted twice on restart.** A kiln serving only GitLab or Gitea re-added its job history to `usage-other.json` at every start; the ledgers are now seeded only when neither exists.
- **Debug hold on GitLab and Gitea.** The hold never triggered there (the result only arrived after the guest was told to release); the host now asks the job API once, bounded, before it answers, and releases when the answer is unknown.
- **Gitea runner sweep.** `keep` compared the VM id with the prefixed runner name and protected nothing; it now spares booting VMs' runners and ones this process registered, returns an error when a delete fails (so the startup cleanup retries) and refuses a listing without `total_count` instead of sweeping part of it.
- **Forge token files** placed by hand or rotated while kiln runs are picked up by the next tick (file modification time), not only after a restart.
- **GitLab fork lookups** that fail (a token without `read_api`, a deleted MR, a 5xx) show as a repo error and are not counted as "fork refused"; the job still gets no VM.
- **Runner cleanup that keeps failing** (startup sweep, hourly sweep, deleting the runners of ended VMs) raises a `cleanup` health item after three attempts, and `warn`s again every tenth.
- **Cache commits.** A failed commit, an overlay that could not be queued, a cache disk that could not be removed, or a parked commit waiting more than 15 minutes with no reader (which also paused the repo's warm VMs) now raise a `cache` health item and are logged; the commit paths have tests with a fake `qemu-img`.
- **GitLab cancel** reports how many VMs it killed and carries a failed job lookup in the answer and the audit note.
- **Notifications.** A destination that gave up on an event counts as failing at once; one that works again is told the problems still active (its `health.raised` may have been lost in the outage); TLS and DNS failures are named; an HTTP client that cannot be built marks the destination failing instead of killing its worker silently.
- **Doctor.** `kiln doctor` no longer reports `starting:` for a revoked token, a missing scope, a mirror hash mismatch or an unsafe or unreadable `tailscale serve` config; only failures that read as "network not up" (and tailscaled not Running) soften. An unreadable serve config is a row. The grace also ends 300 s after the machine booted, so a crash-looping kiln cannot hide errors forever. `stray qemu` compares the count with active VMs.
- Small: the egress probe names a private forge it could not resolve (`egress_forge` health item); `install_id` regenerates only when the file is missing; GitHub token reload errors are logged; leftover VM secrets that cannot be removed are logged.

### Security

- **Docker state in the cache.** When the cache disk is mounted, everything in the cached `/var/lib/docker` except `image`, `overlay2`, `volumes` and `buildkit` is deleted (container records, plugins, swarm state, networks), so a restart-always container or swarm service planted by a compromised trusted job has nothing to restore. dockerd no longer starts before the GitHub job-started hook decides cold or warm. The cache disk mounts as ext4 with `nosuid,nodev`, planted symlinks are removed, and a cold Gitea job waits for the cache disk to be detached before dockerd starts.
- **Verdict gates.** GitHub's fork-refusal hook is unchanged. GitLab and Gitea have a host verdict before any job code: a GitLab runner is paused and never unpaused, `kiln-exec` is one-shot and checks the verdict against the runner's own job response; a Gitea verdict is given only for a job in progress on this VM's own runner; a refused job gets about 10 s to fail cleanly before the VM is killed; the forge runner is always deleted when a gated VM ends; the cache is saved only for a job the forge's API reports as `success` on the VM's own runner with a recorded `ok` verdict. A gate crash, a dropped fanotify queue or a VM that ends between job start and verdict resets the VM at once. More than eight guest secret lines are refused; console matchers are anchored, and a console line cut by a command no longer has its tail parsed.
- **Forge tokens.** A saved token is deleted whenever its forge is removed or added again, and a token whose check overlapped a removal is not saved, so a token can never be sent to an address other than the one it was saved for. An environment-variable token cannot be pointed at a new address through settings saves. Setting a token is audited and raises a security alert; testing one is audited only. Removing or re-adding a forge also deletes its cache disks, so a reused id inherits nothing from the old server.
- **Cross-forge isolation.** Job listings only update VMs of the repo they were read from; the parked cache overlay of repo `x` no longer collides with the cache of a repo named `x.pending` (an existing parked overlay is discarded once). The Gitea job listing reads up to 500 jobs, and a partial or uncounted running-job listing fails closed.
- **Outbound requests.** Alert and forge requests refuse the host's own addresses in every mode, plus 100.100.100.100/200, 168.63.129.16, fd7a:115c:a1e0::53, fd00:ec2::/32 and ISATAP-embedded private addresses, including for tailnet destinations.
- **Residual risks.** A queued fork job can burn one VM per job on every forge (require approval for fork PRs); a Gitea or GitLab token is powerful (Owner on the repo; a Maintainer's `read_api` reads CI/CD variables); the GitLab gate is a script that relies on the runner, not a process-level hold; open egress is still the default. See SECURITY.md.
- **A stale-policy VM survives a failed runner delete (fail-open).** When the forge cannot delete the runner of an idle VM booted under older security settings (egress, debug keys), or the forge is gone, the VM is now killed anyway (warm recycles too) and the delete is retried by the sweep.
- **Cache scrub.** The cache overlay is committed only when the guest printed `kiln: cache scrub ok` after deleting login tokens from the cache disk; a failure, a missing line or a guest that died first discards it. The `job.refused` alert's `reason` is one of a fixed set of phrases and never the forge's or network's error text (URLs, internal hosts), and the new health items carry no error text either.
- `kiln-gate` holds an exec whose process status it cannot read (it allowed it); the bake checks that sysrq is enabled. The gate's decisions are now plain functions with unit tests, behaviour unchanged. The image recipe is 14.

## [0.2.4] - 2026-10-08

### Security

- **QEMU is confined.** Every VM's QEMU runs with libvirt's seccomp policy (`-sandbox on,obsolete=deny,elevateprivileges=deny,spawn=deny,resourcecontrol=deny`): no exec, no setuid, no obsolete syscalls. A job VM's QEMU also starts through `kiln __confine`, which applies a Landlock ruleset first: QEMU sees the system directories, `/dev/kvm` and the standard character devices, the images directory and its repo's cache disk (read-only), and writes only `vms/<id>/q/` (its disks, JIT secret and sockets; kiln's record and logs sit outside it, and QEMU can only append to the console log through its own output). It never inherits a token from kiln's environment (`KILN_GITHUB_TOKEN`, `GITHUB_TOKEN`, `GH_TOKEN`). kiln refuses to start with its data directory under a path QEMU may read (such as `/opt`), connects to QEMU's sockets without following symlinks, and notes on a VM's page when the kernel has no Landlock. It cannot read the GitHub token, App key, dashboard key, other jobs or other repos' caches, or ptrace kiln or other VMs; on Linux 6.12+ it cannot signal them either. A trusted cache overlay is committed only if its qcow2 header names exactly the repo's cache disk and no external data file. New doctor checks "qemu sandbox" and "landlock". A QEMU built without seccomp now fails to start VMs instead of running unfiltered.
- **Release builds run cold.** A job for a pushed tag or a `release` event detaches the repo cache before its first step, so a toolchain planted in the cache by a compromised dependency in some default-branch job never reaches a release build. After every job, `cargo login` and `huggingface-cli login` tokens (`token` and `stored_tokens`) are deleted from the cache before it can be saved. This needs a rebake (recipe 5): launching waits until the image is rebaked, which `auto_rebake` does by itself.
- **Audit log.** Every admitted API write is appended to `<data>/audit.log` as a JSON line (who, from where, what, status, which config keys changed); refused writes go to kiln's log.
- **Stricter dashboard headers:** a hash-based `Content-Security-Policy` (only the page's own inline scripts run), `nosniff`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` and `Permissions-Policy`. The page links only to `https://github.com/` URLs from the API and refuses repo names with dot segments when building GitHub proxy paths.
- **The GitHub proxy writes less:** POST is allowed only to rerun or cancel a run and to dispatch a workflow (no run approvals or deployment reviews).
- **Private files.** The data directory is set to mode 0700 at every start (it inherited the umask before, usually 0775, so other local users could read job logs and repo caches), the systemd unit sets `UMask=0077`, and the token and dashboard key are written atomically with mode 0600 even over an existing looser file.
- rootlesskit's state directory moved to `<data>/rk/<id>`, out of the confined QEMU's reach, and VM records are used at startup only if their id names their own directory.
- **Fail-closed config.** `config.json` is validated at startup with the dashboard's rules; kiln refuses to start on an invalid or unreadable file (only a missing one means the defaults) instead of, for example, treating an unknown `egress` value as open networking.
- `tailscale` CLI calls in the access guard time out after 20 s and fail closed (unknown identity, or local when kiln cannot read its own addresses); failures are logged.
- CI checks dependencies with `cargo deny` (RustSec advisories, licenses, sources), pins `actions/checkout` by SHA, and releases of the public repository carry build provenance attestations.

### Added

- **Host graphs on the Overview.** The Host card's CPU and memory bars are split by job VM, one colour per VM (the same colour marks its tile under Now running), with grey for the rest of the host. Opening the card shows stacked area charts of both over the last 5 minutes, 15 minutes or an hour, scrolling continuously, with a crosshair readout per VM. kiln samples `/proc` every 2 s and keeps an hour in memory (`GET /api/host`).

After saving a setting that only applies at startup (`listen` is the only one), the Overview shows "Restart needed to apply: listen" with **Restart when idle**, which drains like an update (no new VMs, idle ones reaped, running jobs finish, at most the job timeout + 2 min) and re-executes kiln in place, and **Restart now**, which kills running jobs after a confirmation that says so. - The "commit is really on the branch" check applies to every cache-writer branch, not only the default.

### Fixed

- App setup: a failed code conversion (network error, 5xx) can be retried with the same link, setup links survive a kiln restart, and an expired or used code explains how to recover an App GitHub already created.
- App mode: baking and the runner release check work before the App is installed anywhere (that lookup is public and now unauthenticated).
- App mode: a 401 on an installation token always invalidates the cached tokens; Diagnostics reuses a discovery from the last minute.
- The documented fine-grained token permissions now include *Contents: read*, without which caches never saved.

## [0.1.0] - 2026-10-06

First release.

### Added

- Self-hosted CI that boots one fresh rootless QEMU/KVM virtual machine per GitHub Actions job: direct kernel boot (no initrd) of a qcow2 overlay on a frozen Ubuntu 24.04 base image, about 4 seconds to a listening runner.
- `kiln serve`, `kiln bake` (builds the base image from a cloud-init recipe), and `kiln doctor` (checks KVM, tools, disk, memory, image, token, repos, Docker mirror, egress and Tailscale), and `kiln --version`.
- JIT runner registration: single-use, auto-deregistering runners, with the config passed to the guest as an SMBIOS OEM string. Stale offline runners are swept at startup.
- Polling scheduler with ETag-cached GitHub requests and rate-limit pacing. Demand-by-count scheduling per repo and VM size, rotating repo order, memory and vCPU budget, low memory and disk gates, per-repo failure backoff, and a reaper for surplus idle VMs.
- VM sizes by label: `kiln`, `kiln-2cpu`, `kiln-4cpu`, `kiln-8cpu`, `kiln-16cpu`, each scheduled separately.
- Embedded web dashboard with a first-run setup stepper, overview, filterable jobs list with timelines and live console, steps and GitHub logs, repos with workflow dispatch and run rerun and cancel, settings, diagnostics, and favicon and optional browser notifications. Includes an estimate of minutes saved, in-app help, and a hello PR that adds a sample workflow to a repo.
- Tailscale integration: peer list, ping, netcheck, and publishing the dashboard over HTTPS with `tailscale serve`.
- Docker Hub pull-through mirror (pinned registry v3.1.2, SHA-256 verified) with a storage cap, reachable by VMs at `10.0.2.2:5000` with fallback to Docker Hub.
- Per-repo persistent cache disks for Docker layers and package manager and toolchain directories, attached to every job as a private overlay and merged back only by a successful push to the default branch. Parked commits and lock retry for concurrent jobs, and a size reset at 1.2x `cache_gb`.
- Debug hold: a failed job's VM stays up for SSH (`debug_hold_mins`, `debug_ssh_keys`), controlled over the serial console, with host key fingerprints shown on the job page and a Release button.
- Warm pool of pre-booted idle VMs per repo (`warm`, `warm_recycle_mins`).
- Auto-rebake when the runner version or image age goes stale (`auto_rebake`).
- `selftest` and `stacks` workflows, example projects (Node with Postgres, Python with uv, Go, Docker build, Playwright), and a stack compatibility guide.
- Documentation: README, architecture, configuration reference, contributing guide and security policy. Dual licensed under MIT or Apache-2.0.
- Release automation that builds `kiln-<version>-x86_64-linux.tar.gz` with a SHA-256 file when a `v*` tag is pushed.

### Security

- Dashboard access control: tailnet peers identified with `tailscale whois` (owner of the box by default, `allowed_users` to change it), a dashboard key for requests from the box itself, Host header validation against DNS rebinding, a required `x-kiln` header on writes against CSRF, and fail-closed behavior when the box's own tailnet identity is unknown. Tagged nodes are never allowed by default.
- GitHub proxy limited to workflows, runs and jobs of configured repos, with strict path validation. Response headers deny framing and referrers, and prevent caching of API responses.
- Filtered egress (`egress: "filtered"`): each job VM runs in a rootless network namespace (rootlesskit and slirp4netns) with an nftables allow-list for the public internet, DNS and the Docker mirror, blocking the LAN, tailnet, host addresses, metadata and SMTP, with IPv6 off. Capabilities are dropped after the rules load, it fails closed, and a readiness probe gates launches.
- Cache trust rule using GitHub's own record of the job's conclusion, event, branch and commit, so pull requests can read but never poison the cache.
- Hardening against hostile guests: lifecycle lines on the console are accepted once and only forward, a hard VM lifetime cap, capped line length and log size, the hold is granted only after a non-success verdict line; a job can forge that or cancel its own hold, but cannot hold a VM that never ran a job, and SSH published only at hold time (at launch in filtered mode without `rootlessctl`).
- Idle VMs booted under older security settings (egress mode, debug keys) are recycled before they can take a job.
- Mirror binary is pinned and verified by checksum; the mirror is pull-only on host loopback.
